# ProgrammingObsidian

Найкращий спосіб працювати з цим репозиторієм — через [Obsidian](https://obsidian.md/), оскільки структура `vault/`, внутрішні `[[wikilinks]]`, block references і графові налаштування побудовані саме під нього.

Це репозиторій для навчання та структурування теоретичних знань із програмування. Він поєднує чистий `vault/` для щоденної роботи з нотатками та технічний workspace в корені репозиторію для шаблонів, документації, prompts і локальних skills.

## Для чого цей репозиторій

- зберігати знання з програмування в масштабованій Obsidian-структурі
- працювати не лише з книгами, а й з іншими типами джерел
- відокремлювати source notes від evergreen-концептів і практичних playbook-нотаток
- будувати міжджерельні зв'язки без дублювання ідей
- однаково добре працювати вручну або через LLM-асистента

## Базова модель

Модель проста:

1. Усі Obsidian-нотатки живуть тільки в `vault/`.
2. Первинні джерела живуть у `vault/01-Sources/`.
3. Репозиторій підтримує лише чотири типи джерел:
   - `books`
   - `articles`
   - `docs`
   - `courses`
4. Узагальнювані ідеї живуть у `vault/02-Concepts/`.
5. Великі теми й навігаційні MOC живуть у `vault/03-Maps/`.
6. Практичні інструкції та checklist-нотатки живуть у `vault/04-Playbooks/`.
7. Сирі capture-нотатки, ще не прив'язані до конкретного джерела, живуть у `vault/05-Inbox/`.
8. Корінь репозиторію містить лише технічні матеріали: шаблони, документацію, prompts і локальні skills.

## Структура

```text
ProgrammingObsidian/
├── .agents/        # локальні skills та automation-конфігурація
├── _prompts/       # опційні prompts та робочі інструкції
├── _templates/     # шаблони Markdown-нотаток
├── docs/           # технічна документація про архітектуру vault і граф
└── vault/          # єдина папка для відкриття в Obsidian
    ├── 00-Home.md
    ├── 01-Sources/
    │   ├── 00-Sources.md
    │   ├── books/
    │   ├── articles/
    │   ├── docs/
    │   └── courses/
    ├── 02-Concepts/
    ├── 03-Maps/
    ├── 04-Playbooks/
    └── 05-Inbox/
```

## Принципи організації

- `01-Sources/<type>/<slug>/` містить source notes, прив'язані до конкретного джерела
- `02-Concepts/` містить evergreen-нотатки, які можна повторно використовувати між багатьма джерелами
- `03-Maps/` містить MOC-нотатки для великих тем і навігації
- `04-Playbooks/` містить практичні інструкції, checklist і how-to нотатки
- `05-Inbox/` містить сирі capture-нотатки, які ще не розкладені по системі
- source notes не зливаються в один глобальний файл
- синтез і узагальнення виносяться у shared concepts або playbooks, а не дублюються в кожному джерелі
- міжнотаткові зв'язки будуються через `[[wikilinks]]` і block references

## Робочий процес

### У Obsidian

Відкривайте тільки папку `vault/`. Саме вона є робочим knowledge base.

### При додаванні нових матеріалів

1. Спочатку перевіряйте source folder у `vault/01-Sources/<type>/<slug>/`.
2. Потім окремо перевіряйте `vault/02-Concepts/`, щоб не створювати дублікати.
3. Якщо матеріал прив'язаний до конкретного джерела, зберігайте його в source folder.
4. Якщо ідея є узагальнюваною, створюйте або оновлюйте shared concept.
5. Якщо результат є практичним способом дії, створюйте або оновлюйте playbook.
6. Якщо тема вже об'єднує багато джерел і концептів, оновлюйте або створюйте MOC у `vault/03-Maps/`.

### Router для нових нотаток

- `source-local` якщо зміст прив'язаний до конкретного джерела
- `shared-evergreen` якщо це синтезована, повторно вживана ідея
- `topic-map` якщо вже назбиралось кілька джерел і багато пов'язаних концептів
- `playbook` якщо нотатка описує дію, checklist або процедуру
- `capture` якщо це сирий фрагмент, який ще потрібно розкласти

### При роботі з LLM

LLM варто давати завдання працювати лише в межах `vault/` і створювати або оновлювати тільки Markdown-файли. Бажаний процес:

1. знайти пов'язані локальні source notes
2. перевірити shared concepts і релевантні topic maps
3. вирішити, що лишається локальним, а що треба винести у `02-Concepts/` або `04-Playbooks/`
4. оновити Markdown-файли
5. додати внутрішні посилання між нотатками

Репозиторій не прив'язаний до конкретної моделі чи інструмента. Якщо асистент вміє читати локальні файли і редагувати Markdown, цього достатньо.

## Іменування нотаток

- розділи книги: `ch-XX-topic.md`
- звичайні source notes: `note-topic.md`
- локальні або спільні концепти: `concept-topic.md` або коротка тематична назва
- кодові приклади: `code-topic.md`
- підсумки: `summary-topic.md`
- playbooks: `playbook-topic.md`
- capture-нотатки: `capture-topic.md`

Коли є ризик колізій між джерелами, використовуйте path-based посилання, наприклад:

```text
[[01-Sources/books/clean-architecture/03-Concepts/concept-boundary]]
```

Для точних посилань на тези або фрагменти зручно використовувати block references.
