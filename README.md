# ProgrammingObsidian

Репозиторій для ведення програмістської бази знань в Obsidian: конспекти джерел, узагальнені концепти, карти тем і практичні playbook-нотатки.

Проєкт побудований як робочий простір із двох шарів:

- `vault/` містить самі нотатки
- корінь репозиторію містить технічну обв'язку: шаблони, документацію, prompt-и та локальні skills

## Що тут де лежить

```text
ProgrammingObsidian/
├── .agents/        # локальні skills для Codex
├── .obsidian/      # поточна конфігурація Obsidian для цього workspace
├── _prompts/       # допоміжні prompt-и
├── _templates/     # шаблони нотаток
├── docs/           # документація з архітектури й графа
└── vault/          # усі Obsidian-нотатки
    ├── 00-Home.md
    ├── 01-Sources/
    ├── 02-Concepts/
    ├── 03-Maps/
    ├── 04-Playbooks/
    └── 05-Inbox/
```

## Структура знань

### `vault/01-Sources/`

Первинні нотатки, прив'язані до конкретного джерела.

Підтримувані типи джерел:

- `books`
- `articles`
- `docs`
- `courses`

### `vault/02-Concepts/`

Evergreen-нотатки: ідеї, які мають цінність поза межами одного джерела.

### `vault/03-Maps/`

MOC-нотатки для великих тем, навігації та пов'язування кількох джерел.

### `vault/04-Playbooks/`

Практичні інструкції, checklist-и й how-to-нотатки.

### `vault/05-Inbox/`

Сирі capture-нотатки, які ще не пройшли розкладання по структурі.

## Як відкрити репозиторій

У поточній конфігурації найкраще відкривати в Obsidian саме корінь репозиторію, а не лише `vault/`, тому що `.obsidian/` зараз лежить у корені.

Практично це виглядає так:

1. Відкрийте Obsidian.
2. Оберіть `Open folder as vault`.
3. Вкажіть папку `/Users/bohdanne/Desktop/bohdan/ProgrammingObsidian`.
4. Працюйте з нотатками всередині `vault/`.

## Базові правила роботи

1. Усі нотатки створюються лише в `vault/`.
2. Корінь репозиторію не використовується для нових knowledge-нотаток.
3. Перед створенням нової нотатки спочатку перевіряйте, чи вже немає близького файлу.
4. Усе, що належить конкретному джерелу, лишається в папці цього джерела.
5. Те, що узагальнюється між кількома джерелами, виноситься в `vault/02-Concepts/`.
6. Те, що описує процедуру або спосіб дії, виноситься в `vault/04-Playbooks/`.
7. Великі теми з багатьма зв'язками оформлюються через `vault/03-Maps/`.

## Як додавати нове джерело

1. Визначте тип джерела: `books`, `articles`, `docs` або `courses`.
2. Створіть папку `vault/01-Sources/<type>/<slug>/`.
3. Створіть головну source note з назвою джерела.
4. Додайте внутрішні підпапки відповідно до типу джерела.
5. Ведіть первинні нотатки всередині папки джерела.
6. Після цього винесіть узагальнення в `02-Concepts/`, `03-Maps/` або `04-Playbooks/`, якщо це доречно.

## Куди класти нову нотатку

- `source-local`, якщо зміст жорстко прив'язаний до конкретного джерела
- `shared-evergreen`, якщо це узагальнювана ідея
- `topic-map`, якщо це навігаційна або синтезувальна нотатка за темою
- `playbook`, якщо це процедура, checklist або спосіб роботи
- `capture`, якщо матеріал ще сирий і не розкладений

Стислий підсумок не є окремим типом нотатки: його варто тримати всередині `chapter` або `note`, а практичні висновки або залишати там само, або виносити до `playbook`.

## Іменування файлів

- `ch-XX-topic.md` для розділів книги або курсу
- `note-topic.md` для звичайних source notes
- `concept-topic.md` для концептів
- `code-topic.md` для кодових прикладів
- `playbook-topic.md` для практичних інструкцій
- `capture-topic.md` для сирих нотаток

Коли назви можуть конфліктувати між джерелами, краще використовувати path-based wikilinks, наприклад:

```text
[[01-Sources/books/clean-architecture/03-Concepts/architecture-is-important-not-urgent]]
```

Для точних посилань на окремі тези варто використовувати block references.

- `chapter-note.md`
- `source-note.md`
- `concept-note.md`

Якщо створюєте новий тип нотатки, варто одночасно додати для нього шаблон і продумати, як він впишеться в граф та metadata.

## Робота з асистентом

Якщо ви використовуєте Codex або іншого локального LLM-асистента, безпечний базовий режим такий:

1. Дозволяти редагувати лише Markdown-файли у `vault/`.
2. Перед новою нотаткою просити асистента перевіряти наявні source notes і `vault/02-Concepts/`.
3. Просити додавати внутрішні посилання між новими та наявними нотатками.
4. Не змішувати технічні файли з knowledge-нотатками.

Опційний prompt для таких сесій лежить у `_prompts/obsidian-session-prompt.md`.

## Локальні skills та агенти

У папці `.agents/skills/` лежать локальні workflow для Codex. У цьому репозиторії кожен skill має власну інструкцію в `SKILL.md` і свого агента в `agents/openai.yaml`.

На практиці різниця така:

- `skill` це набір правил і кроків для конкретної задачі
- `agent` це готова точка входу з коротким описом і дефолтним prompt-ом, яка запускає відповідний skill

Зараз у репозиторії є один основний локальний skill і відповідний агент.

### `obsidian-source-notes`

Роль: перетворює програмістські джерела на пов'язані Obsidian-нотатки та оновлює вже наявні notes без зайвого дублювання.

Коли використовувати:

- коли у вас є текст із книги, статті, документації або курсу
- коли треба створити або оновити source notes
- коли треба винести ідею в `02-Concepts/`, `03-Maps/` або `04-Playbooks/`
- коли важливо правильно проставити `[[wikilinks]]` і block references

Агент:

- `Obsidian Source Notes`
- призначення: `Turn programming sources into scalable, well-linked Obsidian notes`

## Що використовувати

- для всіх основних задач у цьому репозиторії використовуйте `obsidian-source-notes`
- він підходить для створення, оновлення, лінкування й синтезу нотаток
- якщо в майбутньому виникне потреба в окремому scaffold workflow, його варто додавати лише тоді, коли з'явиться реальна регулярна потреба
