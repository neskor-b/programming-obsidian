## Ціль

Підтримувати репозиторій як двошарову систему:

- технічний workspace для Codex у корені репозиторію
- чистий `vault/` для Obsidian, який містить лише нотатки та навігаційні файли

При цьому основна модель має бути не `book-first`, а `source-first`.

## Чому source-first модель краща

Стара модель була оптимізована лише під книги. Це обмежувало репозиторій у двох місцях:

- первинним джерелом знань вважалася тільки книга
- робочий процес і templates були жорстко зав'язані на `01-Books/`

Для навчання і структурування теоретичних знань з програмування цього замало. На практиці однаково важливими джерелами стають:

- книги
- статті та longreads
- офіційна документація, RFC і specs
- курси, лекції, воркшопи

Тому джерела слід моделювати однаково, а синтез і практичне знання виносити в окремі шари.

## Рекомендована модель

```text
vault/
├── 00-Home.md
├── 01-Sources/
│   ├── 00-Sources.md
│   ├── books/
│   ├── articles/
│   ├── docs/
│   └── courses/
├── 02-Concepts/
│   └── 00-Concepts.md
├── 03-Maps/
│   └── 00-Maps.md
├── 04-Playbooks/
│   └── 00-Playbooks.md
└── 05-Inbox/
    └── 00-Inbox.md
```

## Принцип розділення

- `01-Sources/<type>/<slug>/...` містить source notes, прив'язані до конкретного джерела
- `02-Concepts/` містить evergreen notes, які переживають окреме джерело
- `03-Maps/` містить високорівневі навігаційні нотатки для великих тем
- `04-Playbooks/` містить практичні інструкції, checklist і how-to нотатки
- `05-Inbox/` містить capture-нотатки, які ще не пройшли routing

## Підтримувані типи джерел

Залишати варто лише ті типи, що реально змінюють спосіб читання й конспектування:

- `books`
- `articles`
- `docs`
- `courses`

Не потрібно заводити окремі top-level типи для `talks`, `papers`, `rfc`, `specs`, `blog-posts`, якщо їх можна без втрат вкласти в один із чотирьох типів вище.

## Внутрішня структура джерел

### Книги

```text
vault/01-Sources/books/<slug>/
├── <source-title>.md
├── 01-Inbox/
├── 02-Chapters/
├── 03-Concepts/
├── 04-Code/
└── 05-Summaries/
```

### Articles / docs / courses

```text
vault/01-Sources/<type>/<slug>/
├── <source-title>.md
├── 01-Inbox/
├── 02-Notes/
├── 03-Concepts/
├── 04-Code/
└── 05-Summaries/
```

## Правила створення нотаток

1. Спершу перевіряти локальну папку джерела в `vault/01-Sources/<type>/<slug>/`.
2. Перед створенням нового концепту окремо перевіряти `vault/02-Concepts/`.
3. Якщо нотатка описує конкретну тезу, приклад, структуру розділу чи фрагмент джерела, вона лишається в source folder.
4. Якщо ідея є узагальнюваною і корисною поза межами одного джерела, створюється або оновлюється shared concept у `vault/02-Concepts/`.
5. Якщо результат є практичним способом роботи, checklist або процедурою, створюється або оновлюється playbook у `vault/04-Playbooks/`.
6. Якщо одна тема вже охоплює багато джерел і десятки нотаток, створюється MOC у `vault/03-Maps/`.

## Router для Codex

Під час кожного оновлення нотаток слід приймати окреме рішення:

- `source-local` якщо зміст прив'язаний до конкретного джерела
- `shared-evergreen` якщо це синтезована, повторно вживана ідея
- `topic-map` якщо вже назбиралось кілька джерел і багато пов'язаних концептів
- `playbook` якщо нотатка описує дію, процедуру або checklist
- `capture` якщо матеріал ще сирий і не пройшов структуризацію

## Як уникати дублювання

- Не зливати сирі source notes з різних джерел в один файл.
- Замість цього тримати окремі джерела й збирати синтез у shared concept note.
- У shared concept note додавати секцію `Джерела` з block references на локальні source notes.
- Якщо термін однаковий, але значення в різних джерелах різне, лишати окремі локальні нотатки та пов'язувати їх через `03-Maps/`.

## Правила посилань

- Для source notes використовувати path-based wikilinks, якщо назви можуть повторюватися між джерелами.
- Для точних посилань використовувати block IDs на кшталт `^clean-architecture-ch01-rule-01`.
- У shared concept notes посилатися не лише на файл, а й на конкретний блок локальної source note.

Приклад:

```text
[[01-Sources/books/clean-architecture/03-Concepts/concept-boundary#^clean-architecture-boundary-definition]]
```

## Metadata policy

Щоб vault добре працював і для пошуку, і для графа, варто тримати frontmatter стабільним:

- `type` для типу нотатки
- `scope` для навігаційних хабів і graph filtering
- `source_type` для типу джерела
- `source_slug` для стабільного ідентифікатора джерела
- `source_title` для людської назви джерела
- `sources` для shared notes і playbooks, якщо є кілька джерел

## Граф як частина архітектури

Граф має показувати знання, а не файлову організацію. Тому:

- home та index notes можуть бути приховані або приглушені
- ключові кольори мають бути прив'язані до `type`, а не до шляху файлу
- `scope` використовується для приховування службових navigation hubs
- будь-яка нова metadata-схема має бути сумісна з Juggl, global graph і Breadcrumbs
